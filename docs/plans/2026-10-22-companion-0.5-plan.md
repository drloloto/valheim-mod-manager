# Companion 0.5 — implementation plan

Spec: [2026-10-22-companion-0.5-identity-and-public-endpoint.md](../specs/2026-10-22-companion-0.5-identity-and-public-endpoint.md).
Research: [2026-10-22-companion-direction-critique.md](../research/2026-10-22-companion-direction-critique.md).
Status: not started. 0.4.x is frozen in its architecture; every phase below lands on a `feat/companion-0.5`
branch and is released as 0.5.0-alpha.N of client and companion together. Each phase is its own session,
ends with `vp run ci` green and a status line here.

## Phase A — spike (one session, no product code)

1. `steam://run/892970//+connect%20<host>:2456%20-password%20<pw>/` against the test stack: does the game
   start and join; same for `-joincode` with `-crossplay`.
2. Discord: a throwaway application, scopes `identify connections guilds.members.read`; confirm the Steam
   connection's `id` is the SteamID64 and that `visibility` does not hide it.
3. A real join in the test stack's log: order of `Got connection SteamID` / `PlayFab … Platform ID` and
   `Got character ZDOID from`, and the `Closing socket` id.
4. Result into the research doc's section 6; anything that fails changes the spec before phase B starts.

## Phase B — foundation (0.5.0-alpha.1)

1. **Compose and image** — `proxy` service (Caddy, ACME, HTTP→HTTPS, `tls internal` in LAN mode), Docker
   socket proxy, named volume `companion-state`, companion non-root and unpublished. `onboard.ts` writes the
   new compose; `install.sh` grows `setup` (hostname, setup code) and keeps `update`.
2. **Database** — `bun:sqlite` in `companion-state/companion.db`, migration runner with numbered SQL files,
   tables from spec section 6, a `db.ts` with typed statements. Tests.
3. **Contracts** — `packages/companion-api` (zod schemas, JSON fixtures, `workspace:*`), `/api/v2` router
   skeleton with the auth middleware (cookie or bearer device token, roles), `410` on the 0.4 routes.
4. **Pairing and devices** — `docker exec companion pair`, `POST /auth/pair`, `devices` table, hashed tokens,
   revocation, rate limit on `/auth/*`, `audit` writes. Route tests for no-login / player / admin on every
   v2 route that exists so far.
5. **Remove the gist** — companion: `gist.ts`, `gistsync.ts`, `synccrypto.ts`, `syncsetup.ts`,
   `testing/fakegist.ts`, the `/sync` routes, the landing page's sync setup; client: `gistsync.rs`, sync-code
   paths in `commands.rs` / `server.rs` / `ServerDialog.svelte` / `deeplink.ts`, the `syncCode` and
   `gistToken` fields (migration: profiles with them show "sign in again" once). ADR
   `apps/companion/docs/adr/2026-10-22-http-only-no-gist.md` closes the 2026-10-12 ADR.
6. **Client link by URL** — `ServerLink { url, name, deviceRef }`, `keyring` for the device token, v2 calls
   (`/me`, `/manifest`, `/status`, releases), pairing dialog in `ServerDialog`, deep link
   `valheim-mod-manager://link?url=…`. Role from `/me`.
7. **Verify** — `test/up.ps1` with proxy and LAN mode, `test/e2e.ps1` player path by URL and pairing,
   `vp run ci`, CHANGELOG (0.5.0-alpha.1 for both apps).

## Phase C — Discord (alpha.2)

1. **OAuth** — PKCE flow, `/auth/discord/start|callback`, app registration in settings, `users` upsert with
   Steam id and role snapshot, web session cookie, app sign-in via system browser and
   `valheim-mod-manager://auth?…` → device token. Steam OpenID as the "link Steam" step.
2. **Roles and bootstrap** — guild and role map in `settings`, setup code for the first admin, 24-hour
   re-validation with refresh tokens, loss of role revokes devices.
3. **Whitelist automation** — marker-commented lines in `permittedlist.txt`, adminlist opt-in, hand-written
   lines untouched; tests on the file writer; the test stack checks the file after a fake sign-in.
4. **Player page** — `ui/` becomes the entry page: name + sign-in; after sign-in status, online players, mod
   list, "Open in Mod Manager", `.r2z`. German and English. `apps/invite` deleted, README invite section
   rewritten.
5. **Fake Discord** — `src/testing/fakediscord.ts` (authorize, token, `/users/@me`, `/users/@me/connections`,
   guild member) for `bun test` and the e2e stack.
6. **Verify** — e2e: page → fake sign-in → whitelist line → DEV app sign-in → profile installed; `vp run ci`.

## Phase D — join from Play (alpha.3)

1. `GET /me/join` with env-backed password and crossplay/join code; audit never logs the password.
2. Client: launch arguments `+connect`/`-password` or `-joincode` in `launch_game`, profile switch "join on
   Play", UI copy in `de.ts`/`en.ts`.
3. Page: "Join" as `steam://` link when phase A confirmed it.
4. Verify: argument test in Rust, one manual join against the test stack, `vp run ci`.

## Phase E — 0.5.0

1. **Server area in the app** — `src/routes/server/[tab]` per the 2026-10-14 spec Part B (Overview, Release,
   Players incl. users and devices, Backups, Log, Settings, Audit), fed by v2. `bun run mock:audit` on every
   tab.
2. **Migration 0.4 → 0.5** — `install.sh update` on a 0.4 layout (rehearsed on the production snapshot
   with `vp run test:migration`): lock, installed state, configs unchanged; wizard completes; `companion-token`
   and `sync.json` ignored and named as obsolete in the output.
3. **Docs** — companion README (routes, switches, setup), `docs/architecture.md` (data dir, link model),
   `apps/companion/ROADMAP.md`, CHANGELOGs, release notes with the upgrade steps and "delete your gist".
4. **Release** — `vp run --no-cache ci`, GHCR image (phase 2 of the 2026-10-15 spec, folded in here),
   client 0.5.0 through the existing release workflow.

## Phase F — 0.5.x

- Webhook notifications for lifecycle events (release applied, restart, backup); docs recommend
  DiscordConnector for in-game events.
- Player profiles from `player_sessions` (first/last seen, playtime) in the Players tab.
- Audit view polish, device management for players on the page.
- Discord bot with slash commands only if the group asks for it; own spec first.
