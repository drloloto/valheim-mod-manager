# Companion 0.5: Discord identity, a public HTTPS endpoint, no gist

Date: 2026-10-22. Status: decided, not started. Research and critique:
`docs/research/2026-10-22-companion-direction-critique.md`. Phases:
`docs/plans/2026-10-22-companion-0.5-plan.md`. Supersedes, where they differ, phases 3–5 of
`2026-10-15-monorepo-viteplus-companion-agent-design.md` (the gist is removed, the runtime stays Bun, players
sign in) and the role table of `2026-10-14-admin-ui-in-client-and-monorepo-design.md` ("no separate login").
Everything else in those two specs stands: the companion is an install agent, the admin UI lives in the Mod
Manager, device pairing, a state volume, a socket proxy, `/api/v2` with contracts in `packages/companion-api`.

**0.4.x stays as it is.** No transition mode, no deprecation prompts in 0.4; 0.5 of the client and the
companion are released together and a 0.4 client meeting a 0.5 companion is told to update.

## 1. Goal and scope

One flow for a group of friends: the admin installs the companion next to the game server and gets a URL. A
player opens the URL, signs in with Discord, is on the whitelist ten seconds later, installs the mods with one
click in the Mod Manager and joins the server from the Play button. The admin manages the server from the Mod
Manager. Nobody creates an account, nobody copies a code, nobody needs GitHub.

The companion is a connector between players, the Valheim server and the clients, plus the player entry page.
Admin tools are in the Mod Manager (Server area, `2026-10-14` spec Part B).

Non-goals for 0.5: username/password accounts, an identity provider (Authentik or similar), a relay service
run by the owner, a Discord bot with commands (0.5.x at the earliest, own spec), a mod browser on the server,
a shell into the container, rebuilding DiscordConnector's in-game event feed.

## 2. Reachability

- `compose.companion.yaml` gains a `proxy` service (Caddy) in front of the companion. Caddy terminates TLS
  with automatic ACME certificates for the configured hostname, redirects HTTP to HTTPS, and is the only
  service with a published port (443, plus 80 for the ACME HTTP challenge). The companion listens on the
  compose network only.
- The install wizard asks for a **hostname** (a DynDNS name or an own domain) and checks from outside that
  port 443 answers (a one-shot request to a public echo of our own is not needed: Caddy's ACME success is the
  check). Without a hostname the wizard sets **LAN mode**: Caddy with `tls internal`, bound to the private
  address as today, and Discord sign-in is off because OAuth needs a public redirect URL; pairing is the only
  login then.
- Documented alternative, not built: a provider tunnel in front of the same stack.

## 3. Identity, roles, sessions

### Discord sign-in

- OAuth2 authorization code flow with PKCE, scopes `identify connections guilds.members.read`. The admin
  registers one Discord application per companion in the wizard (client id and secret are stored in the
  database, never in `valheim.env`).
- On sign-in the companion stores or updates a `users` row: Discord id, username, avatar hash, the Steam id
  from the `steam` connection when it is `verified` and not `revoked`, and a snapshot of the member's roles in
  the configured guild.
- Players without a Steam connection in Discord get a "link Steam" step: Steam OpenID 2.0, which returns the
  SteamID64; stored on the same user.
- Roles: the admin configures the guild and, per role, `player` or `admin`. A user with no mapped role is
  signed in but has no access beyond the public page. Roles are re-read on every sign-in and every 24 h with
  the stored refresh token; a user who lost the role loses the whitelist entry and the device tokens.

### Bootstrap and break-glass

- The wizard prints a **setup code** once (10 minutes, single use). The first Discord sign-in that presents
  the code becomes the first admin and picks the guild and roles from the guilds the token can see.
- `docker exec companion pair` prints a pairing code (10 minutes, single use) as in the 2026-10-15 spec. The
  Mod Manager exchanges it for an admin **device token** without Discord. This is the only login in LAN mode
  and the recovery path when Discord is unavailable.

### Sessions and tokens

- Web: an HttpOnly, Secure, SameSite=Lax session cookie, 30 days sliding, stored server-side (`sessions`).
- Mod Manager: sign-in opens the system browser; the companion redirects to
  `valheim-mod-manager://auth?state=…&code=…` (DEV build: `valheim-mod-manager-dev`) and the app exchanges
  the one-time code for a **device token**: 256 bits, shown to the server once, stored as its SHA-256 with a
  device name and last-used time, revocable in the Server area. The app keeps it in the Windows Credential
  Manager (`keyring`), the profile stores only a reference.
- Rate limit on `/api/v2/auth/*` per address; every write lands in `audit` with the acting user or device.

## 4. Whitelist automation

- A user with the `player` or `admin` role and a Steam id gets a line `Steam_<id> # <discord username>` in
  `permittedlist.txt`. Lines the companion wrote are recognised by their comment marker; lines written by hand
  are kept. Removal of the role removes the line. The server reloads the file within 10 s and kicks within 5 s
  more; no restart.
- `adminlist.txt` entries for the `admin` role are an opt-in switch (default off: being a companion admin and
  a game admin are different things).
- Bans stay a manual action in the Server area (writes `bannedlist.txt`, removes the permitted line).
- Players who are only permitted by hand (no Discord) keep working: the automation never deletes a line it did
  not write.

## 5. Joining the game from Play ("ServerConnect" without the mod)

- `GET /api/v2/me/join` (signed in) returns `{address, port, crossplay, joinCode?, password?}`. The password
  is included only for users with a role; it comes from `valheim.env` through the existing env reader.
- The Mod Manager's Play, when the profile is linked and the user has a role, appends `+connect <address>:<port>`
  and `-password <pw>` (or `-joincode <code>` for crossplay) to the game's launch arguments
  (`game.rs`, `commands.rs::launch_game`). A profile setting turns this off ("start the game only").
- The player page offers "Join" as `steam://run/892970//+connect%20…%20-password%20…/` for players without
  the Mod Manager, after the spike verified it. The password never appears in a URL the companion logs, in a
  deep link or in the audit log.

## 6. Data

- `bun:sqlite`, one file `companion.db` in the named volume `companion-state` (outside the game mount), WAL
  mode, migrations as numbered SQL files applied at start.
- Tables: `users` (discord id, username, avatar, steam id, roles json, refresh token, created/seen),
  `sessions` (web), `devices` (token hash, user or `pair` origin, name, created, last used, revoked),
  `player_sessions` (platform id, character name, joined, left, source line hashes; filled by the log follower,
  replaces the 2,000-line tail), `releases` (id, created by, status, applied at, plan summary; the files stay
  in `releases/<id>/`), `audit` (time, actor, action, target, result), `settings` (hostname, guild, role map,
  Discord app id/secret, adminlist opt-in, join settings).
- Stays as files, unchanged: `manifest.json` (the lock), `installed.json`, the BepInEx configs, the pending
  release working state, backups, `valheim.env`.
- Migration from 0.4: `install.sh update` keeps `/config/modmanager` as it is; the companion reads
  `sync-state.json` once for the last release id and then ignores `companion-token` and `sync.json`. The
  admin runs the wizard (hostname, Discord application, setup code). The gist itself is not touched; the
  owner deletes it by hand.

## 7. API

- Only `/api/v2`. Contracts (zod) in `packages/companion-api`, used by the companion, its page and the tests;
  the Rust client mirrors the types by hand with a contract test against the JSON fixtures the package exports.
- Public without sign-in: `GET /health`, `GET /status` (name, version, online count, whether sign-in is
  available), `/auth/*`. Everything else needs the session cookie or `Authorization: Bearer <device token>`.
  `COMPANION_PUBLIC_READ` is gone.
- Routes (admin = `admin` role or a paired device; player = any mapped role):

| route                                                                               | who    | purpose                                           |
| ----------------------------------------------------------------------------------- | ------ | ------------------------------------------------- |
| `GET /me`, `GET /me/join`, `DELETE /me/devices/:id`                                 | player | identity, roles, join data, own devices           |
| `GET /manifest`, `GET /profile.r2z`, `GET /configs…`                                | player | what the server runs, the one-click profile       |
| `GET /players`, `PUT /players/:list`, `GET /players/sessions`                       | admin  | lists, manual entries, history                    |
| `GET /users`, `PUT /users/:id/role-override`, `GET /devices`, `DELETE /devices/:id` | admin  | who signed in, exceptions, device revocation      |
| releases, server lifecycle, backups, env, logs                                      | admin  | as in 0.4, under v2                               |
| `GET /settings`, `PUT /settings`                                                    | admin  | hostname, guild, role map, join, adminlist opt-in |
| `GET /audit`                                                                        | admin  | the audit log                                     |

- A 0.4 client hitting `/api/manifest` or `/api/status` gets `410 Gone` with
  `{"error":"update the Mod Manager to 0.5"}`; the 0.4 client shows it as "not reachable" with the message.

## 8. Sync, invite, deep link

- One transport, HTTP. The client checks on start, every 5 minutes and on Play as today; the Server area uses
  SSE for live views (the log stream exists). Publishing is `POST /releases` with a device token. The gist
  code is removed from the companion (`gist.ts`, `gistsync.ts`, `synccrypto.ts`, `syncsetup.ts`, the fake
  gist) and from the client (`gistsync.rs`, the sync code paths in `commands.rs`, `ServerDialog` code fields).
- The invite is `https://<host>/`. The page shows the server name and "Sign in with Discord"; after sign-in:
  status, who is online, the mod list, "Open in Mod Manager", "Join", `.r2z` download. "Open in Mod Manager"
  is `valheim-mod-manager://link?url=https://<host>`; the app fetches everything else after its own sign-in.
  `apps/invite/join.html` is deleted.
- Client model: `ServerLink { url, name, deviceRef }`. `token`, `syncCode`, `gistToken` are removed; profiles
  that still carry them show "sign in again" once. Role and admin state come from `GET /me`.

## 9. Security baseline

Docker socket through a proxy that exposes only the endpoints the agent uses; the container runs as a
non-root user; state in `companion-state`, nothing secret in `/config`; tokens stored hashed; no secret ever
printed to the log (the setup and pairing codes are the exceptions and are single use); CSP on the page;
dependency pins through the workspace catalog.

## 10. Runtime

Bun stays the companion's runtime and test runner (`bun:sqlite`, `bun test` as a cached `vp run` task). The
move to Node planned as phase 4 of the 2026-10-15 spec is dropped.

## 11. Verification (acceptance for 0.5.0)

- Route and auth tests: every v2 route has a test for "no login", "player", "admin"; the two 0.4 leaks
  (`/env`, the sync secret) cannot recur because the routes no longer exist.
- Test stack: `test/up.ps1` starts proxy and companion with `tls internal` and a fake Discord OAuth server
  (`src/testing/fakediscord.ts`, the way `fakegist.ts` works today). `test/e2e.ps1` runs the player path:
  page, sign-in with the fake, whitelist line appears in `permittedlist.txt`, "Open in Mod Manager", the DEV
  app signs in, installs, and the launch arguments contain `+connect`.
- `vp run test:migration` on the production snapshot: lock, installed state and configs unchanged after the
  0.4 → 0.5 update; the wizard completes; no gist access.
- A real Discord application once, by the owner, against the test stack with a public hostname.
